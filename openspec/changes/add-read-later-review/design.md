## Context

動機は [proposal.md](./proposal.md) を参照。現在のユーザー状態は `item_user_states` に集約され、読書操作はHTTPのアプリケーション操作を経由する。UIは一つのIndexと記事ペインを持ち、`j` と `k` の履歴をクライアント側で管理している。

ブラウザの名前付きウィンドウは一つの閲覧コンテキストであり、同じ名前へ複数URLを開いても複数タブにはならない。さらに、`window.open()`は一回のユーザー操作につき原則一つの新規閲覧コンテキストだけが許可されるため、Webページから複数タブを確実に生成することはできない。

## Goals / Non-Goals

**Goals:**

- 「保存済み」と独立した、永続的なあとで読むキューを提供する。
- 一覧処理中はブラウザへ移動せず、あとから通常のリンク操作で原文をブラウザ翻訳可能なタブへ開く。
- 既存の読書履歴と仮想リストを壊さず、あとで読む固有の `j` / `k` を実現する。

**Non-Goals:**

- ブラウザ固有のタブグループやバックグラウンドタブを制御する。
- 原文ページをiframeへ埋め込む、または保存本文の表示を作り直す。
- チェック状態を読書セッションを越えて永続化する。

## Decisions

### 1. あとで読む状態は既存のユーザー状態へ追加する

`item_user_states` に `is_read_later` と `read_later_at` を追加するマイグレーションを作る。既存行は `is_read_later = 0` とし、実行時のカラム有無によるフォールバックは設けない。追加操作では `is_read_later = 1` と `is_read = 1` を同じトランザクションで更新し、削除操作は `is_read_later = 0` だけを更新する。

別テーブルも検討したが、記事ごとに一行で保持している既存のユーザー状態と更新経路を共有した方が、重複行や集計の不整合を避けられる。

### 2. チェック状態は表示中のIndexに閉じる

「あとで読む」一覧を読み込んだとき、取得した記事IDをクライアント側の選択集合へ入れる。チェック操作はこの集合だけを変更し、APIへは送らない。再読み込みでは再びすべて選択済みになる。

チェック状態の永続化も検討したが、これはその場の一括操作の対象指定であり、記事の長期的な分類ではない。永続化すると、新しく追加された記事や別端末での既定値が分かりにくくなる。

### 3. 原文は通常のリンク、一括操作は削除だけにする

「あとで読む」のタイトルは`href`に正規URLを持つ通常のリンクとして描画する。JavaScriptでクリック方法を上書きせず、⌘クリックによるバックグラウンドタブなどはブラウザの設定と利用者の操作へ委ねる。

同一オリジンのランチャーから`window.open()`を繰り返す方式は実装して検証したが、Chromeでは最初の一件がユーザー操作を消費し、残りが遮断された。また、`popup`指定によりアドレスバーを含む通常のブラウザUIにならなかったため廃止する。OSや特定ブラウザを外部起動する方式も、環境依存性が増え、利用者がブラウザ上で選んだ開き方と一致しないため採用しない。

チェックボックスは一括削除の対象選択だけに使う。UIは選択した記事IDを一つのアプリケーション操作へ渡し、既存のトランザクション内で各記事の`is_read_later`と`read_later_at`を解除する。途中で失敗した場合は全件をロールバックする。

### 4. あとで読むIndexの移動は既存履歴を利用する

通常Indexの `b` は状態更新後に既存の前進処理へ進む。「あとで読む」Indexの `j` は現在記事をキューから外してクライアント一覧から除去し、次の記事へフォーカスする。除去した記事IDは後退履歴へ残し、`k` で記事を復元表示する場合もキューへ再追加しない。したがって、`k` は「現在の記事を削除しない」という要件を満たしつつ、既に消化した過去記事を参照できる。

`k` で戻った記事をキューへ再追加する案は、単なる参照が永続状態を巻き戻すため採用しない。

## Risks / Trade-offs

- [通常クリックでもリンクがNewzsnacとは別のタブへ開く] → 原文確認は明示的なリンク操作とし、Index内の選択はタイトル以外のカード領域で行う。
- [大量の記事を誤って一括削除する] → 対象をチェックボックスと選択件数で明示し、一回の上限を100件にする。削除対象は「あとで読む」状態だけに限定する。
- [定期更新でチェック集合が意図せず初期化される] → 同じフィルターの自動更新では既存IDのチェック状態を維持し、新規に入ったIDだけを既定でチェックする。

## Migration Plan

1. スキーマバージョンを追加し、既存データベースへ `is_read_later` と `read_later_at` を追加する。
2. 読書サービスとアプリケーション操作を追加し、UIより先に永続化と一覧取得を検証する。
3. UI、ショートカット、原文リンク、一括削除操作を追加し、ブラウザテストで一覧消化と状態の維持を検証する。

ロールバック時はアプリケーションコードだけを旧版へ戻せる。追加カラムは旧版から参照されず、データ損失を避けるため削除しない。
