## Context

動機と範囲は`proposal.md`を参照する。
現在の`item_user_states.interest`は`interested`、`not_interested`、未指定を保存でき、読書サービスにも更新処理があるが、操作APIとWeb画面には接続されていない。
分析ワーカーはLM StudioのローカルHTTP APIを利用しているが、記事埋め込みの生成、保存、類似度計算はまだない。
SQLiteは唯一の永続ストアであり、取得済み記事の閲覧操作はLM Studioの可用性から分離する必要がある。

## Goals / Non-Goals

**Goals:**

- 既存の関心状態を画面、CLI、操作APIへ一貫して公開する
- 埋め込みの入力、モデル互換性、類似度計算を再現可能にする
- 1万件程度の個人用データで、閲覧操作を待たせず推薦を更新する
- 推薦の根拠とスコアを利用者が確認できるようにする
- 埋め込みモデルが停止しても読書と関心操作を継続する

**Non-Goals:**

- SQLiteへ外部のベクトル検索拡張を必須導入すること
- 閲覧時間やクリックから暗黙の関心を推定すること
- 異なる埋め込みモデルのスコアを補正して混在させること
- 推薦スコアをLM Studioの生成モデルに再判定させること

## Decisions

### 関心状態は既存の三値を唯一の入力にする

`item_user_states.interest`の`interested`、`not_interested`、`NULL`をそのまま利用する。
「気になった」は`interested`と`NULL`のトグルにし、`not_interested`から設定した場合は`interested`へ置き換える。
`article.interest`操作をWeb、CLI、外部制御で共有し、既存の操作履歴へ記録する。
Web画面では記事操作に「気になった」ボタン、一覧に状態印、サイドバーに「気になった」絞り込みを追加し、キーボードは未使用の`i`を割り当てる。

保存状態を推薦入力として兼用する案は、あとで読む目的と内容への関心が一致しないため採用しない。

### 埋め込みはLM StudioのOpenAI互換APIから取得する

設定`NEWSZNAC_EMBEDDING_MODEL`で埋め込みモデルIDを明示し、既存のローカルLM Studio URLにある`POST /v1/embeddings`へ入力を送る。
埋め込みモデルが未設定または利用不能の場合はランタイム状態へ理由を表示し、ジョブを再試行待ちにする。
チャット用モデルを埋め込みモデルとして暗黙選択しない。

LM StudioのTypeScript SDKを追加する案は、現在のHTTPクライアントと設定境界を二重化するため採用しない。
ネイティブ`/api/v0/embeddings`は非推奨であるため採用しない。

### 埋め込み入力を版付きで決定的に組み立てる

入力は`title`、最新の日本語要約、利用可能な本文の順に、各欄を識別する固定見出し付きで連結する。
モデルのコンテキスト上限と処理量を抑えるため本文は設定した最大文字数までとし、同じUnicode文字列から常に同じ入力を作る。
`input_version`と入力ハッシュを保存し、記事内容、要約、モデル、入力版が変わらない場合はベクトルを再利用する。

要約だけを入力する案は分析完了まで推薦が始まらず、短い要約で固有の論点が失われるため採用しない。
本文だけを入力する案はタイトルの主題が弱まり、長文の処理量が増えるため採用しない。

### ベクトルをSQLiteのBLOBとして保存する

`item_embeddings`へ`Float32Array`のBLOB、次元数、L2ノルム、モデルID、入力版、入力ハッシュ、生成日時を保存する。
一意条件を記事ID、モデルID、入力版とし、同じ組み合わせを置き換えられるようにする。
読み出し時にBLOB長、次元数、有限値、ノルムを検証し、不正な値は推薦に使用しない。

専用ベクトルデータベースやSQLite拡張は配布と復元の手順を増やすため採用しない。
JSON配列は容量と解析コストが大きいため採用しない。

### 関心記事を基点に増分計算する

コサイン類似度は同じモデルID、入力版、次元数を持つベクトル間だけでTypeScript上で計算する。
新しい記事のベクトル生成時は関心記事とのみ比較し、新しい関心を設定した場合はその記事と未読候補を背景ジョブで比較する。
推薦は`item_recommendations`へ候補記事、根拠記事、スコア、モデルID、入力版、計算日時を保存し、候補ごとに最高スコアの根拠一件を保持する。
関心解除時はその記事を根拠とする行を直ちに無効化し、影響した候補だけを残りの関心記事から再計算する。

毎回の記事一覧要求で全組み合わせを計算する案は閲覧遅延につながるため採用しない。
全記事間の近傍表を作る案は、推薦に不要な組み合わせが大半を占めるため採用しない。

### 閾値と表示順を設定可能かつ決定的にする

類似度閾値は`RECOMMENDATION_SIMILARITY_THRESHOLD`で設定し、初期値を`0.75`とする。
「読むべきかも？」一覧はスコア降順、公開日時降順、記事ID降順で並べる。
候補は未読、関心ありでない、興味なしでない記事に限定する。
通常一覧でも条件を満たす記事に印と「気になった『根拠記事』に内容が近い」という説明を表示する。

生成モデルへ推薦理由を書かせる案は、同じベクトル結果でも説明が変動し、推薦更新に追加のモデル処理が必要になるため採用しない。

### 埋め込みと推薦を背景ジョブとして隔離する

収集または分析で記事入力が利用可能になった時点に`embedding`ジョブを登録し、ベクトル保存後に`recommendation`更新を行う。
関心操作はSQLiteの状態更新と古い根拠の無効化までを同期実行し、重い比較はジョブへ委ねる。
接続失敗、不正応答、次元不一致は既存の段階的再試行へ従い、収集、分析、読書操作には波及させない。

## Risks / Trade-offs

- [モデルごとに類似度の分布が異なり初期閾値が合わない] → 閾値を設定可能にし、根拠とスコアを画面で確認できるようにする
- [関心記事の増加で比較回数が増える] → 新規記事は関心記事とのみ比較し、関心変更時の処理を背景ジョブに限定する
- [本文更新と要約更新で埋め込みジョブが重複する] → モデル、入力版、入力ハッシュで冪等化し、最新入力と一致しない結果を採用しない
- [BLOBの破損や次元不一致で誤った推薦が出る] → 読み出し時検証に失敗したベクトルを除外し、再生成を登録する
- [埋め込みモデルがメモリを消費して分析モデルと競合する] → モデルIDを明示設定し、埋め込み処理件数を制限して再試行可能にする
- [古い推薦が関心解除後も見える] → 関心解除と同じトランザクションでその根拠を無効化してから再計算する

## Migration Plan

1. 起動前バックアップ後、`item_embeddings`と`item_recommendations`を追加するマイグレーションを適用する。
2. 関心操作と表示を先に有効化する。既存の`interest`値はそのまま利用する。
3. 埋め込みモデルが設定されている場合だけ、既存記事の埋め込みジョブを新着順に段階登録する。
4. 関心記事と候補記事のベクトルが揃った範囲から推薦を表示する。

ロールバック時は新しいワーカー処理と画面表示を停止する。追加テーブルは既存の収集、分析、閲覧状態から参照されないため、データを保持したまま旧コードへ戻せる。
