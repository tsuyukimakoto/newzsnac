## Context

動機は `proposal.md` を参照。現在は運用ログだけが共通フォーマッターを通り、起動状態と致命的エラーは各エントリーポイントが直接書き出す。詳細分析テレメトリにもレベルがなく、ワーカーの空ポーリングは観察できない。CLIや停止コマンドのJSONは人向けログではなく、外部呼び出し契約である。

## Goals / Non-Goals

**Goals:**

- レベル比較と出力先選択をロガー内部へ集約し、呼び出し側は事象の重大度だけを指定する
- 同じ設定を親プロセス、Web、各ワーカーへ環境変数経由で適用する
- ジョブの再試行動作や収集の障害分離を変えず、失敗を観察可能にする
- テストで最小レベル、時刻、標準出力、標準エラーを差し替えられるようにする

**Non-Goals:**

- JSON応答を人向けログへ変換すること
- イベント名やサービス単位のフィルター
- SQLiteへのログ保存

## Decisions

### ロガーがレベル比較と出力先を所有する

ロガーは `debug`、`info`、`warn`、`error` の4メソッドと最小レベルを持ち、重大度の数値順序を一か所で比較する。DEBUG/INFOは標準出力、WARN/ERRORは標準エラーへ送る。各呼び出し側が `if (config.logLevel === ...)` を持つ案は、レベル追加や閾値の意味を重複させるため採用しない。

### 設定は `NEWSZNAC_LOG_LEVEL` へ集約する

設定値は小文字の4値に限定し、初期値は `info` とする。一般的な最小重大度として扱い、`info` はINFOだけでなくWARNとERRORも含む。子プロセスは親から同じ環境を継承するため、追加のプロセス間設定伝達は行わない。

### 起動状態をINFOへ移す

WebとワーカーのレベルなしJSON起動行を `web.ready`、`collection.ready`、`analysis.ready` のINFOログへ置き換える。これらは人が動作開始を確認するログであり、外部API応答ではない。起動テストと親プロセス監督テストはイベント名で準備完了を確認する。

### ポーリングを毎周期DEBUGで記録する

収集と分析のループは各周期の終了時に処理件数と所要時間をDEBUGで出力する。INFO設定ではロガーが抑制するため、呼び出し側に空件数の条件分岐を置かない。実処理の結果は別のINFOイベントで残す。

### ワーカーがジョブ失敗イベントを通知する

分析ワーカー内部で例外を再試行状態へ保存した直後に、ジョブ情報と原因を失敗イベントとして通知する。ロガーの例外はジョブ状態へ影響させない。LM Studioの詳細テレメトリは有効時だけ生成する現在の設定を残し、出力する場合はDEBUGフォーマットを通す。

### JSON応答とログを別の責務として保つ

CLI、停止コマンド、HTTPレスポンスは呼び出し元が解析するデータなので、ログレベル設定にかかわらず現在のJSONを返す。ログへ統合する案は、`error`設定で正常なコマンド結果が消えるため採用しない。

## Risks / Trade-offs

- [起動ログをJSONから人向けINFOへ変えることで内部テストの期待値が変わる] → イベント名とフィールドを固定し、準備完了を文字列解析に依存しすぎないテストへ更新する
- [DEBUGポーリングが大量になる] → 初期レベルをINFOにし、明示設定時だけ出力する
- [WARN/ERRORを標準エラーへ移すことで単純な標準出力保存に含まれない] → READMEに出力先と必要なリダイレクトを記載する
- [設定読み込み前の構文エラーなどは共通ロガーを通れない] → アプリケーションが捕捉できる起動失敗を対象とし、Node.js自体が開始できない失敗は対象外とする

## Migration Plan

初期値INFOでは、起動と意味のある処理、WARN、ERRORが表示される。詳細調査時だけ `.env` に `NEWSZNAC_LOG_LEVEL=debug` を追加する。ロールバックはロガーと起動出力を以前の実装へ戻すだけで、永続データの移行はない。
