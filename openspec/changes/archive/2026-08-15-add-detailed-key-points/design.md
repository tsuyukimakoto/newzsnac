## Context

分析結果は`item_analyses.reasons_json`へ文字列配列として保存され、読取サービスは文字列配列、記事ペインは単純なリストとして扱っている。分析済み記事を再処理せず、新しい構造へ一度だけ移行した後は新形式だけを扱う必要がある。

## Goals / Non-Goals

**Goals:**

- 保存済み分析を一度のマイグレーションで同じKEY POINTS構造へ統一する
- 新しい分析結果には、見出しと記事内容の説明を必須にする
- 空の説明を持つ移行済み記事と、説明を持つ新規記事を同じ読取経路で表示する

**Non-Goals:**

- 分析済み記事の再分析または新しい観点の補完
- 旧JSON形式を実行時に解釈する互換コード
- KEY POINTSの件数を3件より増やすこと

## Decisions

### 保存列を`key_points_json`へ置き換える

新しいマイグレーションで`key_points_json`を追加し、既存の`reasons_json`文字列配列を`[{"headline": string, "detail": ""}]`へ変換した後、旧列を削除する。新列はNOT NULL、既定値`[]`、有効なJSONという制約を持たせる。旧列を残す案はどちらが正本か曖昧になるため採用しない。

### モデル出力と保存済みデータの検証を分ける

LM Studioの新規出力では各KEY POINTの`headline`と`detail`を空でない文字列として要求する。一方、保存済みデータの読取型はマイグレーションで作られる空の`detail`を許容する。どちらも同じオブジェクト形状であり、旧形式への分岐は行わない。

### 新規分析だけに新しい生成規則を適用する

分析プロンプトで、見出しは論点を短く示し、内容説明は記事中の主張、根拠または影響を1〜3文で記述するよう指示する。既存の分析行や完了ジョブは再投入せず、現在の分析待ち行列が処理する未分析記事だけが新形式を得る。

### 表示は空文字をデータとして扱う

画面は常に`keyPoints`配列を描画し、`headline`を見出し、空でない`detail`を説明として表示する。空文字は移行済みデータの正規値なので、旧形式判定や代替テキストは設けない。

## Risks / Trade-offs

- [マイグレーション前のJSONが不正だと変換できない] → トランザクション全体を失敗させ、旧スキーマのまま保持して不完全な移行を防ぐ
- [新しい出力項目でローカルモデルの生成負荷が増える] → KEY POINTSを最大3件、説明を1〜3文に制限し、構造検証に失敗したジョブは既存の再試行処理へ戻す
- [既存記事は説明がないまま残る] → 利用者が指定した非遡及方針として見出しだけを表示し、再分析は行わない

## Migration Plan

1. `key_points_json`列を制約付きで追加する
2. 既存の`reasons_json`をKEY POINTSオブジェクト配列へ変換する
3. `reasons_json`列を削除する
4. アプリケーションを新列と新しいモデル出力へ切り替える
5. マイグレーション済み既存データと新規分析データの双方をテストする

マイグレーションはトランザクション内で実行される。失敗時はロールバックされるため、アプリケーション更新前のバックアップから復元する以外の逆変換処理は設けない。
